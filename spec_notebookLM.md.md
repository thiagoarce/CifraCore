### Master Spec do CifraCore: Especificação Executiva Consolidada Este documento estabelece a autoridade técnica e o blueprint funcional do ecossistema CifraCore. Como um projeto regido por **Spec-Driven Development (SDD)** , operamos sob a premissa de que a especificação é a "fonte única da verdade" (SSOT) e o código é meramente um artefato gerado. Rejeitamos o modelo "vibe-coding" (iteração baseada em intenções vagas) em favor de contratos rigorosos e arquitetura orientada a dados. #### 1. Fundamentos do Spec-Driven Development (SDD) A filosofia do CifraCore exige que nenhum código lógico seja produzido antes da formalização de artefatos de design. Utilizamos a sintaxe **EARS (Easy Approach to Requirements Syntax)** para derivar requisitos não ambíguos, que são então traduzidos para cenários Gherkin executáveis. Esta abordagem elimina a "alucinação de requisitos" e garante que o Agente de IA atue como um parceiro de implementação, não como um adivinho. ##### Métricas de Governança e Eficiência (Benchmark PharmaSUG) A adoção do modelo "Spec-First" (Nível A3 de governança) em relação ao modelo "Code-First" apresenta ganhos críticos de confiabilidade, conforme validado por estudos de integração em ambientes regulados: | Métrica | Code-First (Vibe-Coding) | Spec-First (SDD/BDD) | Delta de Impacto | | ------ | ------ | ------ | ------ | | **Correção Funcional (F%)** | 20% | **84%** | +64% de precisão algorítmica | | **Qualidade de Integração (I%)** | 0% | **70%** | Redução de 7/10 erros de contrato | | **Assertividade Final (A3)** | Baixa / Inconsistente | **90%+** | Prontidão para Produção | #### 2. SPEC.md: Comportamento Funcional (BDD/Gherkin) Todos os requisitos funcionais abaixo foram validados via notação EARS para garantir cobertura de casos de borda e critérios de aceite claros. ##### 2.1. REQ-001: Abstração Multi-Instrumento gherkin Funcionalidade: Camada de Abstração Multi-instrumento Cenário: Alternância de visualização mantendo sincronia harmônica Dado que a cifra "Hotel California" está carregada com metadados para instrumentos \[Violão, Baixo, Teclado\] Quando o usuário seleciona o instrumento Então o sistema deve remapear o AST musical para o diagrama de E as tablaturas devem ajustar o número de cordas e afinação conforme a tabela de tipos Exemplos: | instrumento_alvo | cordas | visualizacao_esperada | | "Violão" | 6 | Diagramas de acordes tradicionais | | "Baixo" | 4 | Tablatura e nota fundamental | | "Teclado" | N/A | Shape de mão direita (V-O-C) | ##### 2.2. REQ-002: Liderança Democrática e Sync Real-time gherkin Funcionalidade: Sincronização de Sessão (Líder/Seguidor) Cenário: Propagação de transposição harmônica instantânea Dado que os dispositivos "A", "B" e "C" estão pareados na sessão "Palco_Alpha" E "A" possui o papel de "Líder" Quando o Líder altera o tom da música de "E Major" para "G Major" Então o sistema deve despachar um evento de transposição via WebSocket para "B" e "C" E o componente de visualização em todos os dispositivos deve renderizar os novos acordes em &lt; 100ms ##### 2.3. REQ-003: Resiliência de Palco (Offline & Wake Lock) gherkin Funcionalidade: Modo Show Ininterrupto Cenário: Manutenção de estado em falha de rede e inatividade Dado que o "Modo Show" está ativo no PWA Quando o sistema detecta ausência de sinal de rede (offline) Então o sistema deve servir o MusicalAST via IndexedDB local sem degradação E o sistema deve invocar a Wake Lock API para impedir que o SO apague a tela ##### 2.4. REQ-004: Interface HID (Pedais Bluetooth) gherkin Funcionalidade: Controle Hands-free via Comandos HID Cenário: Interpretação de comandos de pedal e tratamento de cliques duplos Dado que um pedal Bluetooth está pareado como entrada HID Quando o pedal envia um comando "ArrowDown" (Single-click) Então o sistema deve realizar o auto-scroll para a próxima seção (ex: Verso -&gt; Refrão) Quando o pedal envia um comando "ArrowDown" (Double-click) em menos de 300ms Então o sistema deve ignorar o scroll duplo e executar a ação "Retornar para a Intro" #### 3. PLAN.md: Arquitetura e Contratos de Tipo A stack tecnológica é composta por **SvelteKit** (Frontend reativo), **Supabase** (Backend/Edge Functions) e **PostgreSQL** (Storage). ##### 3.1. Contratos de Dados (Type Contracts) Abaixo, a definição rigorosa das entidades centrais. O MusicalAST é o núcleo de inteligência do sistema. typescript // Estrutura de Árvore de Sintaxe Abstrata para Músicas interface MusicalNode { type: 'chord' | 'text' | 'section_header' | 'tab_line'; value: string; metadata?: { duration?: number; transpose_offset?: number; finger_position?: number\[\]; }; } interface MusicalAST { version: string; sections: { id: string; label: string; // Intro, Solo, Bridge content: MusicalNode\[\]; }\[\]; } interface Cifra { id: string; uuid: string; metadata: { title: string; artist: string; original_key: string; bpm: number; }; ast: MusicalAST; supported_instruments: string\[\]; } interface SessaoPalco { session_id: string; leader_id: string; current_song_id: string; current_key: string; scroll_y_percent: number; last_updated: number; // Timestamp para evitar Spec Drift } ##### 3.2. Arquitetura de Integração e Validação "Fail-Fast" O CifraCore utiliza um **Middleware de Validação OpenAPI/JSON Schema** . Qualquer payload (Request/Response) que divergir do contrato definido em 1 bit será automaticamente rejeitado antes de atingir a camada de lógica de negócios. Isso impede a propagação de dados sujos e facilita a depuração imediata por agentes de IA e humanos. ##### 3.3. Scraping e Processamento AST As Edge Functions do Supabase atuam como o motor de ingestão. O parser converte o texto bruto em MusicalAST através de análise léxica, identificando padrões harmônicos via @tonaljs. Este processo é isolado e determinístico. #### 4. TASKS.md: Roadmap Data-First Seguimos rigorosamente o fluxo **Specify -> Plan -> Task -> Implement** . Nenhuma tarefa pode avançar para a fase de implementação sem o aceite do "Auditor" sobre o plano técnico. \* **Fase 1: Especificação e Motor Musical** \* Formalizar requirements.md via EARS para os 10 principais domínios de cifras. \* Implementar Parser AST com 100% de cobertura de testes de contrato. \* **Gate de Qualidade:** Verificação de conformidade pelo Agente Auditor. \* **Fase 2: Infraestrutura Local-First** \* Implementar Service Workers para cache de MusicalAST em IndexedDB. \* Configurar sincronização Realtime via Supabase com resolução de conflitos por timestamp. \* **Fase 3: Interface Reativa (SvelteKit)** \* Desenvolver visualizador de cifras baseado estritamente nos cenários do SPEC.md. \* Integração com Wake Lock API e suporte a eventos HID (Bluetooth Pedals). #### 5. constitution.md: Leis Técnicas Imutáveis 1. **Dependências Musicais:** O uso da biblioteca @tonaljs é mandatório. É proibido reimplementar lógica de transposição ou detecção de intervalos. 2. **Proibição de Edição Manual:** Alterações manuais em pastas /generated (tipos, schemas, mocks) resultarão em rejeição imediata do commit. Toda mudança deve ser feita na Spec. 3. **Spec Registry:** Todas as chamadas de bibliotecas externas devem ser validadas contra o **Spec Registry** (baseado no modelo Tessl) para evitar alucinações de API por parte da IA. 4. **Validação Human-in-the-Loop:** Cifras extraídas via scraping requerem promoção manual para o ambiente de produção após revisão do AST. 5. **Rastreabilidade Total:** Todo commit deve referenciar um ID de requisito (ex: REQ-001) ou cenário Gherkin. #### 6.
